# v0.8 Scheduler Safety Kernel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a backend-neutral lease and fencing contract with a single-host, multi-process SQLite implementation that rejects stale worker writes atomically.

**Architecture:** Scheduler value objects and typed errors live in a focused `scheduler.py` module; `ports.py` defines the storage protocol; `SQLiteRepository` supplies short `BEGIN IMMEDIATE` transactions. Existing synchronous runtime APIs remain compatible while the scheduler CLI exposes evidence and a deterministic two-connection safety campaign.

**Tech Stack:** Python 3.10+, standard-library `sqlite3`, dataclasses, protocols, `unittest`, existing zero-dependency CLI.

## Global Constraints

- Preserve all v0.7 APIs and open existing v0.7 SQLite databases without a migration command.
- SQLite scheduler safety is limited to multiple processes on one host; do not claim network-filesystem or multi-node safety.
- All scheduler tests use injected ISO-8601 UTC timestamps; no sleeps or live network calls.
- Lease and heartbeat durations are integer seconds from 1 through 86,400.
- No model, tool, filesystem, or network execution may occur inside a database transaction.
- Every stale fenced mutation must roll back without partial artifacts, reviews, attempts, performance, events, or task changes.

CREATE TABLE IF NOT EXISTS task_claim_fences (
    goal_id TEXT NOT NULL,
    task_id TEXT NOT NULL,
    last_token INTEGER NOT NULL,

);
CREATE TABLE IF NOT EXISTS task_claims (
    claim_id TEXT PRIMARY KEY,

- [ ] **Step 3: Implement deterministic recovery**

Inside `BEGIN IMMEDIATE`, find active claims with `expires_at <= now`. For a running task,
inspect the latest same-task delegation. Set the task blocked for `submitting`, `unknown`, or
`interrupted`; otherwise set it pending. Mark claim expired and append exactly one
`task.claim_expired` event. Never reopen a terminal task.

- [ ] **Step 4: Implement one fenced outcome transaction**

Revalidate exact active identity and `expires_at > now`, task/attempt/review identity, task
terminal target, and artifact reference. In one transaction insert the optional artifact,
attempt, review, performance, and all events; update the final task payload; then mark the
claim committed. Any validation or SQL failure rolls back the whole unit.

Test successful PASS/FAIL outcome commits, stale tokens, mismatched task IDs, duplicate event
rollback, risky delegation blocking, accepted/completed resumability, and persistence after
