# Agent Society Loop v0.7 Delegation Trust Control Plane Design

## Objective

Version 0.7 turns the v0.6 A2A transport into an operator-governed trust
control plane. A remote deployment may execute production work only when one
content-addressed policy rule allows the exact task, agent, card, context, and
resource envelope, and when required external conformance evidence is present
and fresh.

This version also adds two distinct diagnostics:

- a read-only production-readiness doctor for card drift, deployment, policy,
  and attestation state;
- a deterministic local reliability campaign that proves the runtime remains
  fail-closed under ambiguous sends, identity drift, interrupted tasks,
  unsupported output, and exhausted polling.

## Evidence and ecosystem findings

The official A2A organization now publishes three separate validation tools:

- `a2a-tck` is the Technology Compatibility Kit and emits
  `reports/compatibility.json` with summary, per-requirement, per-transport,
  and Agent Card data;
- `a2a-inspector` is an interactive web debugger with basic card checks;
- `a2a-itk` validates multi-hop SDK interoperability and transport matrices.

The v0.7 implementation targets the machine-readable TCK 1.0 report schema
observed at upstream revision
`5996b79f9cefa6fc390980e383e358a66fb9e49e`. It records the operator-supplied
upstream revision rather than silently assuming that a mutable `main` branch
is evidence.

## Approaches considered

### 1. Implement a new in-project conformance suite

This would keep setup small but duplicate the official TCK and make this
project the authority for its own interpretation of A2A. It is rejected.

### 2. Download and execute the TCK from the runtime

This offers one-command automation but requires installing a large external
toolchain, executing repository code, selecting a mutable revision, and
granting network authority to the runtime. It conflicts with the existing
operator-owned command and dependency boundaries. It is rejected.

### 3. Import content-addressed official evidence and enforce local policy

The operator runs a pinned official TCK revision, then imports its JSON report.
Agent Society Loop validates the report schema and the relevant HTTP+JSON/MUST
results, binds the report digest to the registered card identity, and uses it
as one input to a deterministic policy decision. This is the selected design.

## Scope

v0.7 includes:

- immutable delegation policy documents and per-task-type activation;
- deterministic ALLOW/DENY decisions persisted before a first network send;
- direct parsing and content-addressing of A2A TCK compatibility JSON;
- freshness and required-attestation policy gates;
- per-rule context and request/result/poll/deadline ceilings;
- policy identity in delegation, trace, event, and benchmark evidence;
- read-only production-readiness doctor;
- deterministic local fault campaign;
- CLI workflows, examples, bilingual documentation, migration, and release.

## Non-goals

- The runtime does not clone, install, or execute TCK/Inspector/ITK code.
- Imported evidence is operator-attested and content-addressed, not
  cryptographically signed by the upstream tool.
- No arbitrary policy language, model-generated rules, Python callbacks, OPA
  runtime, Rego evaluator, or shell execution is accepted.
- No automatic policy activation, deployment, fallback, resend, or promotion.
- No inbound A2A server, streaming, webhook, file/media, or multi-turn support.
- No claim of cross-node scheduling. SQLite remains a single-host persistence
  boundary. A true multi-node control plane requires a storage/lease abstraction
  and a network-safe transactional backend and is a separate version.

## Policy document

The operator imports strict JSON with no unknown fields:

```json
{
  "policy_id": "production-research",
  "version": 1,
  "default": "deny",
  "rules": [
    {
      "rule_id": "research-agent-v1",
      "task_types": ["research"],
      "agent_ids": ["research-agent"],
      "card_sha256s": ["<64 lowercase hex>"],
      "allowed_context_sections": ["review_feedback"],
      "max_request_bytes": 65536,
      "max_result_bytes": 131072,
      "max_polls": 12,
      "total_timeout_seconds": 45,
      "required_attestation_kinds": ["a2a-tck"],
      "max_attestation_age_hours": 168
    }
  ]
}
```

`default` must be `deny`. Wildcards are not supported. Every task type may
match at most one rule for one exact agent/card identity; ambiguity is DENY.
Rules cannot raise runtime ceilings. Effective limits are the minimum of the
runtime configuration and the matched rule.

`DelegationPolicy.digest` is SHA-256 over canonical JSON of policy identity and
rules. Import is immutable by digest. Activation binds one task type to one
digest and records `activated_by`; activation never follows a mutable policy ID.

## Conformance attestation

`parse_a2a_tck_report` accepts raw UTF-8 JSON bytes plus an existing remote
registration, a 40-character upstream source revision, and a tool version.
It validates:

- the strict TCK top-level sections;
- ISO-8601 summary timestamp;
- protocol specification version `1.0`;
- `must_compatibility == 100.0%`;
- no MUST requirement with `FAIL` status;
- an HTTP+JSON transport section with zero failed tests;
- an Agent Card whose exact selected interface, protocol version, binding, and
  required skills still match the registration.

The attestation stores the raw report SHA-256, card SHA-256, TCK source
revision, tool version, observed time, compatibility metrics, and passed state.
It never stores bearer values. A failing report may be stored for audit but
never satisfies a policy.

## Policy decision

Before creating a new delegation, `DelegationPolicyEvaluator.decide` resolves
the active policy for the task type and emits a `PolicyDecision` containing:

- goal, task, attempt, agent, model, and card identity;
- policy ID, digest, and selected rule ID;
- ALLOW or DENY;
- stable reason codes rather than private free-form errors;
- effective context sections and resource limits;
- exact attestation IDs used as evidence.

The unique decision identity is `(goal_id, task_id, attempt_no, agent_id)`.
A stored decision is immutable. DENY is persisted and raised as `PolicyDenied`;
the remote worker converts it to `WorkerBlocked` so the engine records a
score-zero attempt and blocks instead of retrying or falling back.

Accepted or completed delegations resume using their original policy decision.
Policy changes cannot rewrite the authority under which an already-created
remote task was sent. New attempts require a new current decision.

## Executor data flow

For a new remote attempt:

1. Resolve any existing durable delegation. Resume known accepted/completed
   state before considering a new policy.
2. Ask the evaluator for a decision and persist it.
3. Stop on DENY before allocating a message ID or performing network I/O.
4. Build outbound context using the intersection of registration and rule
   allowlists.
5. Apply the minimum of runtime and policy limits.
6. Persist PREPARED and SUBMITTING with policy decision identity.
7. Send and follow the existing no-resend, polling, cancellation, and local
   review lifecycle.

Delegation, `RemoteExecution`, benchmark evidence, and engine events expose only
the decision ID, policy digest, rule ID, card digest, and sanitized state.

## Doctor

`a2a doctor AGENT_ID` performs no Send Message. It fetches the current Agent
Card with existing bounded transport and reports checks for:

- raw card digest and exact interface/skill drift;
- registered profile/model identity;
- active deployment identity for each mapped task type;
- active policy digest and an ALLOW simulation;
- required, passing, fresh TCK attestations.

Each check has a stable ID, PASS/FAIL status, and safe summary. Overall readiness
passes only when every required check passes. The report is observational and
does not activate policy or change deployment.

## Local reliability campaign

`a2a self-test` runs in memory and performs no external network calls. Scripted
clients exercise five invariants against the real executor and repository:

1. an ambiguous Send Message is sent once, becomes UNKNOWN, and is not resent;
2. a changed task ID fails the delegation;
3. auth/input interruption becomes INTERRUPTED;
4. unsupported URL/raw output is rejected before artifact creation;
5. poll exhaustion makes exactly one cancellation and ends CANCELED.

The command returns a structured report and nonzero status on any invariant
failure. It is a runtime safety diagnostic, not evidence that a remote server
conforms to A2A.

## Persistence

SQLite adds:

- `delegation_policies(policy_digest, policy_id, payload)`;
- `policy_activations(task_type, policy_digest, payload)`;
- `conformance_attestations(attestation_id, agent_id, card_sha256, payload)`;
- `policy_decisions(decision_id, goal_id, task_id, attempt_no, agent_id, payload)`.

Older registrations, delegations, and outcomes deserialize with empty policy
evidence. Existing v0.6 accepted/completed records remain resumable. New CLI
production sends require an active policy; this fail-closed migration is
intentional and documented.

## CLI

The A2A group gains:

- `a2a policy validate FILE`;
- `a2a policy import FILE`;
- `a2a policy list`;
- `a2a policy activate DIGEST --task-type TYPE --by NAME`;
- `a2a policy simulate --task-type TYPE --agent AGENT`;
- `a2a attest-tck AGENT REPORT --source-revision SHA --tool-version VERSION`;
- `a2a attestations [AGENT]`;
- `a2a doctor AGENT`;
- `a2a self-test`.

All inspection output supports JSON. No command accepts executable text.

## Testing and release gates

- Domain tests cover strict schema, canonical digest, unknown fields, overlap,
  transition identity, and age boundaries.
- Storage tests prove reopen, immutability, uniqueness, and old-payload defaults.
- TCK fixtures cover passing, failed MUST, wrong transport/version, card drift,
  malformed percentages, unknown fields, and source revision validation.
- Executor tests prove DENY before network, effective-limit enforcement,
  original-decision resume, and evidence propagation.
- Engine and CLI tests prove the four production gates: deployment, policy,
  attestation, and explicit remote opt-in.
- Doctor and reliability tests cover every reported invariant.
- Full Python 3.10-3.14 CI, source compilation, package build, fresh-wheel CLI,
  and credential scans remain release requirements.

## Follow-on architecture

v0.8 should introduce a repository protocol, transactional lease/fencing
contracts, and a network-safe backend before enabling concurrent orchestrator
replicas. Policy decisions and delegation identities from v0.7 become the
authority records consumed by that scheduler.
