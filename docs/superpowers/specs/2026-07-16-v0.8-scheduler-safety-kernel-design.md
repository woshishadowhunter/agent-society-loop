# v0.8 Scheduler Safety Kernel Design

## Status

Approved for implementation under the standing recommendation-first authorization. This
release deliberately stops at correct multi-process scheduling on one host. It does not
claim network-distributed scheduling or exactly-once external side effects.

## Problem

The v0.7 runtime persists goals, tasks, attempts, delegation evidence, and policy decisions,
but `LoopEngine` still assumes one process owns execution. It reads a pending task, changes
it to running, executes unbounded work, and later writes the result. Two processes can select
the same task, and a paused process can resume after a replacement worker has taken over.
Without an ownership epoch, the old process can overwrite newer state.

The next generation of the loop therefore needs a scheduling correctness layer before it
needs more agents, more models, or a multi-node deployment switch.

## Considered Approaches

### A. Safety kernel first (selected)

Add backend-neutral scheduler contracts, durable worker sessions, transactional task claims,
leases, monotonic fencing tokens, and fenced outcome commits. Implement the contract in
SQLite for multiple processes on one host and prove it with two independent connections.

This is the smallest release that establishes reusable correctness invariants. A later
PostgreSQL implementation can preserve the public contract while replacing SQLite locking.

### B. Rewrite the whole engine around a worker service

This would expose end-to-end parallel execution sooner, but it combines correctness,
process management, engine refactoring, deployment, and operations in one change. Failures
would be difficult to isolate and compatibility risk would be high.

### C. Adopt a workflow platform immediately

Temporal or a similar platform already provides durable execution, but adopting it now would
add infrastructure and a new programming model before this project's own ownership and
evidence contracts are stable. It remains a future adapter option rather than a v0.8 runtime
dependency.

## Design Sources

- SQLite permits multiple readers but only one writer. `BEGIN IMMEDIATE` obtains the write
  transaction before claim selection, so competing claimers serialize at a short critical
  section.
- WAL improves reader/writer concurrency but requires all database processes to run on the
  same host. The runtime must reject network-filesystem/distributed claims in its docs.
- Kubernetes Lease objects establish the useful vocabulary of holder identity, renewal time,
  and expiry.
- Temporal demonstrates that worker loss must be detected separately from workflow lifetime,
  and that durable state transitions are the recovery boundary.
- PostgreSQL `FOR UPDATE SKIP LOCKED` is the intended queue primitive for a future network-safe
  repository adapter, not for this SQLite release.

## Scope

v0.8 delivers:

1. Typed worker-session and task-claim contracts.
2. A narrow `SchedulerRepository` protocol independent of SQLite.
3. Durable worker registration and heartbeat with session replacement protection.
4. Transactional claim of one exact ready task.
5. Lease renewal, voluntary release, and deterministic expired-claim recovery.
6. A strictly increasing fencing token for every new claim of a task.
7. One atomic, fenced outcome commit covering artifact, review, attempt, performance,
   completion event, final task state, and claim state.
8. Inspection, recovery, and deterministic safety self-test CLI commands.
9. Bilingual operations and architecture documentation.

v0.8 does not deliver:

- a network worker daemon, message broker, or multi-node scheduler;
- automatic parallel execution inside `LoopEngine`;
- exactly-once model, tool, HTTP, or filesystem side effects;
- PostgreSQL or managed workflow-service deployment;
- live lease renewal from a background execution thread.

The synchronous engine remains compatible. The new kernel is the required foundation for
moving engine execution behind worker processes in the next release.

## Domain Contracts

### WorkerSession

Each running process registers an operator-chosen `worker_id` and a fresh opaque `session_id`.
The durable record contains capabilities, start time, latest heartbeat, and expiry time.
Registering a new session for the same worker ID replaces the old session. Heartbeats from the
old session fail closed, preventing a restarted process from extending its successor's life.

Identifiers use the existing safe identifier convention. Lease and heartbeat durations are
finite integer seconds from 1 through 86,400.

### TaskClaim

A claim binds:

- `claim_id`;
- `(goal_id, task_id)`;
- execution `worker_id` and `session_id`;
- selected specialist `agent_id`;
- positive, task-local `fencing_token`;
- `acquired_at`, `renewed_at`, and `expires_at` UTC timestamps;
- status: `active`, `committed`, `released`, or `expired`;
- bounded terminal reason.

Claim history is immutable except for renewal and the single active-to-terminal transition.
There can be at most one active claim for a task. Every replacement claim receives a token
larger than all previous tokens for that task.

### Errors

- `WorkerSessionRejected`: missing, expired, or superseded worker session.
- `ClaimUnavailable`: the task is not pending/ready or another unexpired claim owns it.
- `StaleClaim`: the claim is absent, terminal, expired, superseded, or its identity/token does
  not match.

Expected claim contention returns `None`; malformed identity and stale mutation attempts raise
typed errors.

## Repository Protocol

`SchedulerRepository` exposes only scheduler operations:

```python
register_worker(session: WorkerSession) -> WorkerSession
heartbeat_worker(worker_id: str, session_id: str, *, now: str, ttl_seconds: int) -> WorkerSession
get_worker(worker_id: str) -> WorkerSession | None
list_workers() -> list[WorkerSession]
claim_task(goal_id: str, task_id: str, worker_id: str, session_id: str,
           agent_id: str, *, now: str, lease_seconds: int) -> TaskClaim | None
renew_claim(claim_id: str, worker_id: str, session_id: str, fencing_token: int,
            *, now: str, lease_seconds: int) -> TaskClaim
release_claim(claim_id: str, worker_id: str, session_id: str, fencing_token: int,
              *, now: str, reason: str = "") -> TaskClaim
reap_expired_claims(*, now: str) -> list[TaskClaim]
commit_claim_outcome(claim: TaskClaim, task: Task, artifact: Artifact | None,
                     attempt: Attempt, review: Review, performance: PerformanceRecord,
                     events: Sequence[Event], *, now: str) -> TaskClaim
get_claim(claim_id: str) -> TaskClaim | None
list_claims(goal_id: str | None = None) -> list[TaskClaim]
```

The protocol is intentionally narrow. It does not expose SQL or require all existing runtime
persistence methods to be abstracted in one release.

## SQLite Schema And Transactions

Three additive tables preserve compatibility with v0.7 databases:

- `scheduler_workers(worker_id PRIMARY KEY, session_id, expires_at, payload)`;
- `task_claim_fences(goal_id, task_id, last_token, PRIMARY KEY(goal_id, task_id))`;
- `task_claims(claim_id PRIMARY KEY, goal_id, task_id, worker_id, session_id,
  fencing_token, status, expires_at, payload)`.

A partial unique index allows only one row with `status = 'active'` for each task. Connections
use foreign keys, a bounded busy timeout, and WAL for file-backed databases. In-memory
databases retain their supported journal mode.

Claim, renew, release, reap, and commit operations use explicit `BEGIN IMMEDIATE`, contain no
model or network work, and always commit or roll back before returning.

Claiming revalidates all of these facts inside the transaction:

1. the exact worker session exists and is not expired;
2. the goal exists and is running;
3. the task exists and is pending;
4. every declared dependency is succeeded;
5. no unexpired active claim exists;
6. the next fencing token is persisted atomically;
7. task status becomes running in the same commit as the active claim.

## Fenced Outcome Commit

Long-running execution happens outside the database transaction. Before accepting its result,
the repository revalidates exact claim ID, worker session, fencing token, active status, and
lease expiry. It then atomically writes all local outcome evidence and final task state before
marking the claim committed.

An expired or replaced worker cannot persist an artifact, review, attempt, performance update,
event, or task transition through this API. A failed validation writes nothing.

External systems do not understand this local fencing token automatically. Tool and transport
adapters must continue using idempotency keys, content identities, and durable A2A delegation
records. A future adapter may forward the token to an external service that supports epochs.

## Expiry And Recovery

Reaping is explicit and deterministic; it does not depend on a background timer. For each
expired active claim, one transaction marks the claim expired and appends a
`task.claim_expired` event.

- A normal local task returns from running to pending.
- An A2A task with a durable `submitting`, `unknown`, or `interrupted` delegation is changed to
  blocked because automatic replay could duplicate or mis-handle remote work.
- Accepted or completed A2A delegations may return to pending because v0.7 resumes polling or
  replays the stored result without submitting a second remote task.
- Terminal task states are never reopened.

Reaping does not directly make a goal terminal. The existing outer loop observes a blocked
task and follows its normal blocked-goal path.

## CLI

The `scheduler` command group provides JSON-capable operations:

- `scheduler workers` lists sessions and expiry state;
- `scheduler claims [--goal-id]` lists claim history;
- `scheduler reap --at <UTC>` performs explicit recovery;
- `scheduler self-test` runs a socket-free deterministic campaign.

The self-test uses a temporary file database and two independent repository connections. It
must prove exclusive claim, renewal, expiry/reclaim with increasing token, stale commit
rejection with zero partial writes, and successful current-token commit.

No command starts a daemon or claims multi-node support.

## Testing

Tests use explicit UTC timestamps and no sleeps. Required scenarios:

1. domain validation and serialization round trips;
2. new session supersedes the old session and rejects its heartbeat;
3. two SQLite connections cannot both claim one ready task;
4. dependency and goal-state eligibility is revalidated transactionally;
5. renewal requires exact active ownership and cannot revive expiry;
6. expiry creates a higher-token replacement claim;
7. stale fenced commit creates no artifact, attempt, review, event, or task mutation;
8. valid fenced commit is atomic and survives reopen;
9. risky A2A expiry blocks while accepted/completed recovery remains resumable;
10. v0.7 databases open and existing 193 tests remain green;
11. CLI inspection, recovery, and self-test output are stable.

## Release Boundary

The public claim is precise: v0.8 provides a backend-neutral scheduling safety contract and a
single-host, multi-process SQLite implementation. The next release may add a worker service
and PostgreSQL adapter, but only after both pass the same ownership/fencing conformance suite.
