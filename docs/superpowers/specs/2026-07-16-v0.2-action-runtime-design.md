# Seed Society v0.2 Action Runtime Design

## Purpose

Version 0.2 turns the deterministic orchestration kernel into a runtime that can use real models and real tools without losing auditability. Every model decision and tool action must be structured, persisted, bounded, and attributable to one goal and task.

This is the first implementation slice of the longer roadmap. It deliberately builds the execution substrate before autonomous repository mutation or pull-request creation.

## Success criteria

The release is complete when all of the following are true:

1. Planner, worker, and reviewer roles can be driven by an injected model provider using strict JSON contracts.
2. A worker can request registered tools through a bounded tool loop and cannot invoke undeclared tools.
3. Tool calls are classified as read, write, or execute risk and evaluated by a deterministic policy before execution.
4. Calls requiring approval create durable approval requests, pause the goal without consuming a failed attempt, and resume after approval or rejection.
5. Model calls, tool calls, reviews, approvals, and goal transitions produce linked trace spans with timing and status.
6. A `maintain` CLI command can read a public GitHub issue, inspect a local repository through safe tools, and produce a reviewed maintenance proposal without modifying the repository by default.
7. Existing deterministic demos and all v0.1 public behavior continue to pass.

## Non-goals

- Automatically applying patches or creating pull requests without approval.
- Distributed workers or a network queue.
- Reinforcement learning or autonomous production policy mutation.
- Vector embeddings or a hosted memory service.
- Full MCP or A2A protocol support. The local tool contract is intentionally shaped so an MCP adapter can be added next.
- A web dashboard.

## Architecture

### Structured model agents

`ModelProvider` remains the model transport boundary. A new strict JSON helper parses exactly one JSON object, rejects malformed or schema-incompatible output, and never silently repairs model output.

Three adapters implement the existing role protocols:

- `ModelPlanner` produces a validated list of task objects.
- `ModelWorker` alternates between structured tool requests and a final artifact.
- `ModelReviewer` produces a `Review` with a verdict, score, defects, and summary.

Provider prompts contain role instructions, compact task context, available tool schemas, and explicit output schemas. Runtime credentials are never injected into prompts, trace attributes, or persistence.

### Tool runtime

Each tool declares:

- stable name and description;
- JSON-compatible input schema;
- risk level: `read`, `write`, or `execute`;
- an `invoke(arguments)` implementation.

`ToolRegistry` owns discovery and duplicate-name validation. `ToolExecutor` validates the requested tool, evaluates `ToolPolicy`, checks durable approval state when required, invokes the tool, and returns a structured `ToolResult`.

The default policy allows read-only tools and requires approval for write and execute tools. Unknown tools and paths outside a configured workspace are denied. Policy decisions are deterministic application code, never model output.

### Durable approval

An approval request is keyed by a stable call fingerprint and contains goal, task, tool, redacted arguments, reason, status, and timestamps. Pending approval raises `ApprovalRequired` to the engine.

The engine changes the running task back to pending, transitions the goal to `paused`, persists an event, and returns a report. No attempt or failure outcome is recorded because the action did not execute.

`approve` and `reject` CLI commands update the request. Resuming an approved goal moves it back to running. The repeated tool call uses the same fingerprint, observes the durable decision, and either executes or returns a deterministic rejection error.

### Trace model

A trace span records:

- `span_id`, `trace_id`, optional `parent_span_id`;
- `goal_id`, optional `task_id` and `agent_id`;
- kind and name;
- status, start and end timestamps, duration;
- JSON-compatible redacted attributes and optional error category.

The trace ID is stable for one goal run. Spans are append-only after completion. Existing domain events remain the human-readable audit log; spans provide machine-readable causal and timing data for evaluation and later learning.

### GitHub maintenance intake

The first vertical workflow accepts a public GitHub repository URL and issue number. It uses a read-only GitHub HTTP client to retrieve issue title, body, labels, and URL. A workspace toolset exposes bounded file listing, file reading, and text search under a user-supplied local checkout.

The model planner creates inspection, proposal, and review tasks. The final artifact contains:

- issue summary and acceptance interpretation;
- relevant files and evidence;
- proposed changes;
- test plan;
- risks and approval requirements.

The default workflow does not change the checkout. This makes the first real integration safe and reproducible while providing the trajectory data needed for the subsequent patch-application slice.

## State changes

`GoalStatus.PAUSED` is non-terminal.

```text
running -> paused     pending approval
paused  -> running    approval resolved and run resumed
paused  -> failed     required action rejected
```

Calling `run` on a paused goal with unresolved approvals returns the paused report unchanged. Calling `resume` after approval continues execution. Rejection fails the goal with an explicit reason rather than retrying the denied action.

## Failure handling

- Malformed model JSON fails the current attempt and remains visible in review and trace data.
- Unknown or schema-invalid tool calls return structured tool errors to the worker and count against the tool-step budget.
- Policy denial is final for that tool call and is reported to the model.
- Pending approval pauses execution and consumes neither task attempts nor action budget.
- Provider and tool exceptions are redacted before persistence.
- Tool loops are bounded independently from task attempts by `max_tool_steps`.

## Testing strategy

- Domain tests cover risk levels, approval states, paused transitions, and span validation.
- Storage tests prove approvals and spans survive reopen and approval updates are atomic.
- Tool tests use real temporary directories and deterministic tools; HTTP is isolated at the GitHub client boundary.
- Model-agent tests use a scripted provider to verify prompts, strict parsing, tool loops, and malformed output.
- Engine tests prove pause, approval, resume, rejection, and unchanged attempt accounting.
- CLI tests cover maintenance intake, approval commands, and stable JSON output.
- The full existing suite remains the regression gate.

## Compatibility and migration

SQLite initialization adds tables with `CREATE TABLE IF NOT EXISTS`; existing databases remain readable. Existing goal statuses, CLI commands, deterministic adapters, and protocol implementations continue to work. New constructor parameters have safe defaults, so v0.1 callers require no changes.

## Follow-on slice

After v0.2 is stable, the next spec will add isolated patch application, command execution, test verification, human-approved pull-request creation, MCP adapters, and champion/challenger evaluation over recorded traces.
