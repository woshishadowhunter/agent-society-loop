# Seed Society v0.3 Guarded Execution Design

## Purpose

Version 0.3 upgrades repository maintenance from a read-only proposal into a
locally executable, human-gated change loop. A model may inspect files, request
content-addressed writes, run operator-configured verification checks, inspect
the resulting diff, and repair failed checks. Every mutation remains bounded,
approved, traceable, and recoverable.

This release intentionally stops before commits, pushes, or pull-request
creation. Remote publication will be a separate milestone that consumes durable
verification evidence produced here.

## Success criteria

1. Reading a file returns its SHA-256 identity in addition to its content.
2. A write must name a relative path, complete UTF-8 content, and the exact
   expected pre-write SHA-256 value (or `missing` for a new file).
3. Writes are atomic, reject symlinks and protected paths, enforce size limits,
   and fail on stale content instead of overwriting it.
4. The first write to each path stores a durable pre-change snapshot scoped to
   the goal. Later writes preserve that original recovery point.
5. A restore tool can return all goal-owned paths to their original state, but
   refuses to overwrite files that changed outside the recorded mutation chain.
6. Verification commands are selected by stable names from an operator-provided
   allowlist. Models cannot supply shell text, arguments, environment variables,
   working directories, or timeouts.
7. Check execution uses `shell=False`, a fixed workspace, a bounded timeout and
   output limit, and records a durable result tied to the current workspace
   digest.
8. The maintenance CLI supports `--apply` plus repeatable named `--check`
   declarations. Without `--apply`, v0.2 read-only behavior is unchanged.
9. A guarded run can pause for a write or execute approval, resume in another
   process, apply a change, observe a failed check, repair the file, pass the
   check, and produce a reviewed final artifact.

## Safety boundary

### Workspace ownership

Guarded execution requires a Git worktree that is clean when the run is
created. This prevents recovery or later publication from conflating pre-existing
human edits with agent-owned changes. The workspace root is fixed for the run.

Protected paths include `.git`, `.worktrees`, virtual environments, build
outputs, caches, and the runtime database when it is inside the workspace.
Absolute paths, traversal, symlinks, junctions, and non-UTF-8 content are denied.

### Content-addressed writes

`workspace_write_file` accepts:

- `path`: a relative workspace path;
- `content`: the complete replacement UTF-8 text;
- `expected_sha256`: the hash returned by the latest read, or `missing`.

The tool validates the expected identity before writing. It writes a temporary
file in the destination directory and atomically replaces the target. This
avoids partial files and prevents a stale model observation from clobbering a
newer human edit.

### Durable recovery

The repository stores one snapshot per `(goal_id, path)` containing whether the
path originally existed, its original UTF-8 content, original hash, latest
agent-written hash, and restoration state. Snapshot creation and updates are
committed before and after the filesystem replacement respectively.

`workspace_restore_changes` restores every non-restored snapshot only when the
current file hash equals the latest recorded agent hash. A mismatch is reported
and left untouched. Recovery is idempotent and survives process restart.

### Named verification

Checks are supplied by the operator at composition time as a mapping from a
short name to an argument vector. `workspace_run_check` accepts only the name.
It invokes `subprocess.run` with `shell=False`, the fixed workspace directory,
an explicit timeout, a minimal inherited environment, and bounded output.

The result includes pass/fail, exit code, duration, bounded stdout/stderr, and a
workspace digest derived from Git status and diff. The durable record is scoped
to the goal and check name. This evidence will later gate PR publication.

## Tool surface

Read-only mode keeps:

- `workspace_list_files`
- `workspace_read_file`
- `workspace_search`

Guarded mode adds:

- `workspace_write_file` (`write` risk)
- `workspace_diff` (`read` risk)
- `workspace_run_check` (`execute` risk)
- `workspace_restore_changes` (`write` risk)

The existing default policy therefore pauses before every write, restore, or
check. Approvals are fingerprinted from exact arguments and cannot authorize a
different content payload or check.

## Maintenance workflow

`maintain` remains read-only by default. With `--apply`, the goal evidence tells
the planner to produce an implementation task whose worker must:

1. inspect relevant files and hashes;
2. request content-addressed writes;
3. inspect the diff;
4. run every configured named check;
5. repair failures and rerun checks;
6. return a final artifact containing changed files, check results, residual
   risks, and a statement that no remote action occurred.

The reviewer must reject an implementation artifact that lacks change and
verification evidence. The outer and inner loop budgets remain authoritative.

## Failure handling

- Stale expected hashes return a structured tool failure; they do not write.
- A process interruption after snapshot persistence but before replacement
  leaves a harmless unused snapshot.
- A process interruption after replacement is recoverable because the snapshot
  and latest agent hash are durable.
- Timeout terminates the check and records a failed result.
- Decode errors use replacement markers in bounded command output and never
  expose the parent process environment.
- Failed checks are observations, not runtime exceptions, so the worker can
  repair and rerun within its tool-step budget.
- Rejected write or execute approval fails the goal through the existing engine
  path without consuming a task attempt.

## Non-goals

- Arbitrary shell commands supplied by a model.
- Binary file editing, file deletion, rename, chmod, or package installation.
- Git commit, push, pull-request creation, or merge.
- Containers, operating-system sandboxing, or distributed workers.
- Automatically approving any mutation.

## Follow-on slice

Version 0.4 will add a publication gate. It will require a clean pre-run
workspace, a branch under an allowed prefix, a successful verification record
matching the current workspace digest, and explicit approval before commit,
push, or pull-request creation.
