# Agent Society Loop v0.5 Interoperable Evolution Design

## Purpose

Version 0.5 makes two previously implicit boundaries explicit: external tools
enter through the stable Model Context Protocol, and model/agent upgrades enter
through a reproducible champion/challenger evaluation gate. Neither discovery
nor a higher average score grants authority by itself.

## Standards baseline

- MCP protocol revision `2025-11-25`, the latest stable revision on the build
  date. The adapter supports the initialization handshake, `tools/list`
  pagination, and `tools/call` over stdio JSON-RPC.
- A2A `1.0.0` informs future task and agent-card boundaries, but remote agent
  delegation is not enabled in this release. Tool governance and evaluation must
  be stable before opaque remote execution is added.

## MCP safety contract

1. Server commands and arguments are operator configuration, never model input.
2. The client uses `shell=False`, a minimal environment, bounded messages,
   request timeouts, and a dedicated stdout reader.
3. Protocol negotiation accepts only explicitly supported stable revisions.
4. Every discovered tool requires an operator-supplied `ToolRisk`; unknown tools
   or missing risk mappings are not registered.
5. MCP names are namespace-prefixed to prevent collisions.
6. Server annotations are informational and cannot lower local risk.
7. `isError` tool results become local tool failures; protocol and transport
   errors are sanitized.
8. Once adapted, MCP tools pass through the existing schema, approval, tracing,
   and action-budget runtime exactly like local tools.

## Evaluation model

A benchmark is an immutable set of cases. Each case declares task type,
input/context, acceptance criteria, criticality, and a stable case ID. A
candidate runner produces an artifact and latency. A separate evaluator returns
pass/fail and a score. Raw case outcomes are persisted before aggregation.

The benchmark digest includes every case and criterion. Candidate identities
include agent ID and model ID. This prevents a result from being reused after a
benchmark, model, or prompt identity changes.

## Promotion gate

A challenger is recommended only when all conditions hold:

- at least five benchmark cases;
- no critical case failure;
- pass rate is not below the champion;
- mean score improves by at least the configured delta (default 2 points);
- no per-case score regression exceeds the configured limit (default 10);
- p95 latency stays within the configured ratio (default 1.5x).

The decision stores every metric and failed gate. A recommendation does not
change production routing. `promote` is a separate explicit operator action that
persists who promoted which evaluation. Promotion is rejected if the benchmark
was not recommended or its identities no longer match.

## Production routing

The latest deployment record for a task type names one champion agent. The
engine filters eligible candidates to that champion before normal selection. If
the champion is unavailable or incompatible, the goal blocks rather than
silently falling back to an unapproved candidate. Task types without a deployment
record retain performance-weighted routing.

## Non-goals

- Online reinforcement learning, automatic prompt mutation, or self-approval.
- Treating production traffic as an unconsented experiment.
- MCP sampling, elicitation, resources, experimental tasks, or HTTP transport.
- A2A remote task execution, streaming, push notifications, or agent-card trust.
