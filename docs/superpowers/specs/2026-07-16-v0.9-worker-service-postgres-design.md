# v0.9 Worker Service and PostgreSQL Runtime Design

**Status:** Approved for implementation

## Purpose

v0.8 made ownership of one exact task safe inside a same-host SQLite deployment. v0.9 turns that kernel into an operable execution plane:

- a coordinator can plan a goal without executing it;
- independent worker processes discover ready work, claim it, execute it, review it, and commit one fenced outcome;
- leases remain alive while model or tool calls are running;
- SQLite remains the zero-configuration same-host backend;
- PostgreSQL becomes the network-safe multi-host backend and owns the complete execution transaction.

This release does not split claims into PostgreSQL while storing task outcomes in SQLite. A backend that owns a claim must also own the goal, task, artifact, review, attempt, performance, event, and final claim update in the same transaction.

## User-visible workflows

### Enqueue

`agent-society enqueue goal.json --db society.db` creates, validates, and plans a goal, then returns while the goal is `running` and its tasks are `pending`.

The PostgreSQL form uses `--database-url` or `AGENT_SOCIETY_DATABASE_URL`. Credentials are never written to events or JSON output.

### Work

`agent-society worker run --db society.db --worker-id worker-a --agent-id spec-analysis` starts a long-running process. `--once` processes at most one claim and is the deterministic operational primitive used by tests and jobs.

The process:

1. registers a unique session generation;
2. heartbeats the session;
3. atomically finds and claims one ready task compatible with its configured agents;
4. runs execution and review outside a database transaction;
5. renews the session and claim on an independent repository connection;
6. discards local output if lease ownership is lost;
7. atomically commits the fenced outcome;
8. repeats after bounded polling, or drains on shutdown.

### Inspect and recover

Existing scheduler inspection and reaping commands remain. Worker JSON output distinguishes `idle`, `committed`, `lost`, and `stopped` outcomes. Operators can identify the claim, fencing token, goal, task, and resulting state without exposing model prompts or credentials.

## Components

### Coordinator

`LoopEngine.plan(goal_id)` exposes planning as a durable lifecycle operation. It is idempotent after a valid task graph exists and refuses terminal goals. The synchronous `run()` path remains available and retains its active-claim exclusion.

### Scheduler repository

`SchedulerRepository.claim_next_task(...)` receives an immutable mapping of supported task types to agent IDs and returns `ClaimedTask(claim, task)`. The repository chooses the oldest deterministic ready task and changes it from `pending` to `running` in the same transaction that creates the active claim.

Readiness means:

- the parent goal is `running`;
- the task is `pending`;
- every dependency in the same goal is `succeeded`;
- the task type appears in the worker assignment mapping;
- no active claim exists for that goal/task identity.

SQLite uses `BEGIN IMMEDIATE`, which serializes writers on one database file. PostgreSQL uses a short `READ COMMITTED` transaction and `SELECT ... FOR UPDATE SKIP LOCKED`, which PostgreSQL documents as appropriate for multiple consumers of a queue-like table. The locked task row is held only while the claim record and running task state are written.

Official references:

- PostgreSQL `SELECT` locking and `SKIP LOCKED`: https://www.postgresql.org/docs/current/sql-select.html
- PostgreSQL transaction isolation: https://www.postgresql.org/docs/current/transaction-iso.html
- PostgreSQL `UPDATE ... RETURNING` and queue batching: https://www.postgresql.org/docs/current/sql-update.html

### Lease maintainer

The default lease maintainer runs in a daemon thread and creates its own repository connection through a factory. It never shares a SQLite connection with the execution thread. At each interval it heartbeats the worker session and renews the exact claim using worker ID, session ID, claim ID, and fencing token.

Any `StaleClaim`, `WorkerSessionRejected`, or persistence failure marks ownership as lost. The main worker may allow the in-flight Python call to return, but it must not persist its artifact or review. Python threads cannot safely terminate arbitrary provider calls, so cancellation remains cooperative.

### Outcome builder

Worker execution reuses the existing `Worker`, `Reviewer`, `MemoryManager`, and performance scoring contracts. It produces the same domain records as the synchronous engine. A pass requires an artifact, `PASS`, and the configured minimum score. A failed review returns the task to `pending` unless attempts are exhausted. `WorkerBlocked` moves the task and goal to `blocked`.

`ApprovalRequired` is not silently retried. The claim is released to `pending`, the durable approval remains authoritative, and the goal is paused by a fenced repository operation.

### Atomic goal reconciliation

`commit_claim_outcome` also evaluates the post-update task set under the same transaction:

- all tasks succeeded -> goal `succeeded`;
- committed task failed -> goal `failed`;
- committed task blocked -> goal `blocked`;
- otherwise -> goal remains `running`.

The transaction writes at most one terminal goal event. A crash after commit cannot leave a terminal task graph behind a running goal.

### PostgreSQL repository

`PostgreSQLRepository` uses psycopg 3 and JSONB payloads while keeping normalized columns for scheduler predicates and indexes. It implements the execution-plane repository used by enqueue, worker, status, and scheduler commands. Broader governance features remain SQLite-backed until their complete transactions are ported; the CLI rejects unsupported PostgreSQL commands rather than falling back or dual-writing.

The initial PostgreSQL schema includes:

- `goals`, `tasks`, `artifacts`, `reviews`, `attempts`, `events`;
- `agents`, `performance`, `knowledge`, `deployments`;
- `scheduler_workers`, `task_claims`, `task_claim_fences`;
- the normalized task status, task type, position, and goal status needed for indexed claiming.

Schema creation is additive and idempotent. Runtime connections use server-generated UTC timestamps for production claim decisions. Explicit timestamps remain supported by the conformance API so deterministic cross-backend tests can prove identical boundaries.

## Safety invariants

1. One goal/task identity has at most one active claim.
2. Every successful reclaim increments a task-local fencing token.
3. A stale session, claim, token, or expired lease cannot commit.
4. Claim ownership and all outcome records share one database transaction.
5. Long model/tool execution holds no task row lock or write transaction.
6. Lost lease output is discarded even if the model call later succeeds.
7. A worker session generation supersedes every older generation with the same worker ID.
8. Dependency readiness is checked by the repository while claiming.
9. Worker shutdown stops new claims and drains only the current claim.
10. External tool effects are at-least-once unless the tool itself uses an idempotency key derived from `claim_id` and `fencing_token`.

## Conformance testing

The same behavioral suite runs against SQLite and PostgreSQL:

- exclusive `claim_next_task` across competing workers;
- dependency ordering;
- deterministic priority;
- lease renewal;
- expiry and monotonic reclaim;
- stale outcome rejection and rollback;
- current atomic outcome commit;
- terminal goal reconciliation;
- worker session supersession.

GitHub Actions starts a PostgreSQL service and runs the PostgreSQL suite on Python 3.12. The existing Python 3.10-3.14 SQLite matrix remains unchanged. PostgreSQL support is an optional dependency so the default offline install stays small.

## Explicit non-goals

- message broker integration;
- Kubernetes manifests or autoscaling;
- forced cancellation of arbitrary Python/model calls;
- exactly-once external side effects;
- migrating A2A governance, evaluation, publication, or maintenance transactions to PostgreSQL in this release;
- cross-backend replication or fallback.

## Release gate

v0.9 is releasable only when:

- the complete existing suite passes;
- worker service tests prove renewal, lost-lease discard, retry, terminal outcomes, and clean shutdown;
- both backends pass one shared scheduler conformance suite;
- PostgreSQL integration runs against a real GitHub Actions service;
- clean-wheel `enqueue -> worker --once -> status` succeeds for SQLite;
- bilingual documentation states backend and exactly-once boundaries accurately.
