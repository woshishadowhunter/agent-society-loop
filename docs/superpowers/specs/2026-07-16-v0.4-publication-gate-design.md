# Seed Society v0.4 Publication Gate Design

## Purpose

Version 0.4 turns a verified local maintenance result into a reviewable GitHub
pull request. Publication is a separate, explicit capability that consumes v0.3
workspace snapshots and verification results. It cannot publish model claims;
it can publish only a concrete workspace digest for which every configured check
has a durable passing result.

## Required invariants

1. Publication is disabled unless the operator explicitly enables it.
2. The current branch must not be the protected base branch and must begin with
   an operator-configured prefix.
3. Every current Git change must be owned by the goal's workspace snapshots.
4. Every configured check must have a passing result for the current workspace
   digest after the latest write.
5. The exact repository, remote, branch, base, title, body, changed paths,
   workspace digest, and check names enter the durable approval fingerprint.
6. Only goal-owned paths are staged. No `git add --all` is permitted.
7. Commit, push, and pull-request creation persist progress after each side
   effect and resume idempotently after interruption.
8. A changed publication payload cannot reuse an earlier approval or publication
   record.
9. The tool never merges, force-pushes, deletes branches, or publishes from a
   dirty protected branch.

## State machine

```text
prepared -> committed -> pushed -> pull_request_created
```

The publication record is keyed by goal and stores the approved payload digest,
commit SHA, push state, PR number, and PR URL. Re-entry validates branch and
payload identity, then resumes from the last durable state. A completed record
returns the same result without another network mutation.

## Git boundary

All Git subprocesses use argument vectors with `shell=False`, a fixed workspace,
bounded timeouts, and sanitized errors. The tool stages only snapshot-owned paths,
creates one normal commit, and pushes `HEAD` to the configured remote without
force flags. Existing staged changes or non-goal workspace changes fail the gate.

## GitHub boundary

An injected pull-request client receives repository, head branch, base branch,
title, and body. The default client uses the GitHub REST API and a runtime token
that is never persisted. Before creation it searches open pull requests for the
same head/base pair, making retries idempotent even if the process stopped after
GitHub accepted the request but before local persistence.

## CLI

`maintain --apply --publish` adds `workspace_publish_pull_request`. Publication
requires `GITHUB_TOKEN`, at least one named check, and operator options for base,
remote, and allowed branch prefix. The same options must be supplied on resume.
Read-only and local apply modes remain unchanged.

## Non-goals

- Merge, review approval, force push, branch deletion, release publishing.
- Arbitrary Git commands supplied by a model.
- Publishing untracked human files or pre-existing staged changes.
- Bypassing repository branch protection or GitHub permissions.
