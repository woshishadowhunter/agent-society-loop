# Agent Society Loop v0.6 A2A Delegation Design

## Purpose

Version 0.6 lets a promoted specialist run behind an independent A2A server
without weakening the local goal lifecycle, reviewer gate, budgets, memory, or
audit trail. A remote agent is an opaque executor, not a new trust root.

The release targets A2A `1.0`, the latest stable protocol on the design date.
It implements a strict polling subset of the `HTTP+JSON` binding: public Agent
Card inspection, `SendMessage`, `GetTask`, and `CancelTask`.

## Approaches considered

### Official Python SDK

The official SDK offers broad protocol coverage, but would introduce an async
dependency stack and optional streaming, webhook, extension, and transport
surfaces that the current synchronous zero-dependency runtime does not need.

### Strict standard-library HTTP+JSON subset

This is the selected approach. It preserves the zero-runtime-dependency
package, exposes only the operations needed for bounded delegation, and keeps
all remote authority behind operator registration and existing promotion.

### Generic HTTP worker

A generic POST adapter would be smaller, but it would discard Agent Card
identity, task lifecycle, cancellation, protocol versioning, and interoperable
evidence. It does not satisfy the project architecture.

## Protocol boundary

The client sends `A2A-Version: 1.0`, uses
`Content-Type: application/a2a+json`, and accepts no protocol fallback. It
supports these endpoints relative to an operator-pinned interface URL:

- `POST /message:send`
- `GET /tasks/{id}`
- `POST /tasks/{id}:cancel`

The public card is fetched from an exact operator-supplied URL, normally
`/.well-known/agent-card.json`. The card must declare the exact pinned
`HTTP+JSON` interface at protocol version `1.0` and every registered skill ID.

Streaming, push notifications, extended cards, list operations, extensions,
multi-turn continuation, file parts, gRPC, and JSON-RPC are not implemented.

## Trust and registration

Remote discovery never writes an executable agent profile automatically. The
operator first inspects a card, then registers all trust inputs explicitly:

- local `agent_id`;
- card URL and expected raw SHA-256 digest;
- exact interface URL;
- task-type to Agent Card skill-ID mapping;
- optional bearer-token environment variable name;
- allowed outbound context sections;
- whether insecure loopback HTTP is allowed for local development.

Registration refetches the card and requires the exact digest. Redirects,
embedded URL credentials, fragments, unsupported schemes, and non-loopback
plain HTTP are rejected. Production TLS uses the standard CA verifier.

The generated `AgentProfile.model_id` is `a2a:<full-card-sha256>` and its
`execution_kind` is `a2a`. A changed card therefore has a different candidate
identity and cannot inherit old benchmark or promotion authority. Registration
is immutable; rotation creates a new local agent identity and a new evaluation.

JWS verification is intentionally not claimed in v0.6. Exact card digest
pinning is the local trust mechanism. Bearer values are read from the named
environment variable per request and are never persisted or printed.

## Outbound disclosure policy

The remote envelope always contains only the task type, description, and
acceptance criteria. Additional context sections are operator allowlisted from:

- `goal`;
- `task_context`;
- `dependency_artifacts`;
- `review_feedback`;
- `knowledge`.

The default allowlist is only `review_feedback`. Sensitive-key redaction runs
before serialization. Payload bytes, normalized result bytes, response bytes,
poll count, request timeout, total deadline, and polling interval are bounded.
Models cannot change these values or choose an endpoint.

Only text and structured-data response parts are accepted. Structured data is
canonicalized to JSON text. File, URL, audio, video, unknown, empty, and
oversized outputs are rejected before they become local artifacts.

## Durable delegation state

`RemoteAgentRegistration` stores the trust configuration. `DelegationRecord`
stores:

- local delegation ID, goal ID, task ID, attempt number, and agent identity;
- durable client-generated message ID;
- outbound payload digest and card digest;
- remote task ID and exact A2A task state;
- local lifecycle state and poll count;
- normalized result content and SHA-256 when completed;
- sanitized error category, operator cancellation identity, and timestamps.

The unique identity is `(goal_id, task_id, attempt_no, agent_id)`. Every state
transition is persisted before the next network action. A completed normalized
result is stored because the local process may stop after remote completion but
before the engine creates its normal artifact.

The local lifecycle is:

```text
prepared -> submitting -> accepted -> completed
                      |            -> failed/rejected/canceled/interrupted
                      -> unknown
```

`accepted` may contain A2A submitted or working states. Input-required and
auth-required become `interrupted`; v0.6 does not transmit credentials or
follow-up input in band.

## Ambiguous submission rule

A2A says Send Message may be idempotent, not that every server guarantees it.
The message ID and `submitting` state are persisted before the POST. A timeout,
connection loss, malformed successful response, or server failure after the
request may mean the remote task exists without a known task ID. The record
becomes `unknown`, and the local goal blocks through a typed `WorkerBlocked`
exception. The runtime never automatically resends an ambiguous submission.

Known client-side rejection before task creation can fail normally and use the
next bounded local attempt. An interrupted process that finds `submitting`
also converts it to `unknown`. Accepted delegations resume by polling the same
remote task ID; completed delegations replay their persisted normalized result.

## Polling and cancellation

`SendMessage` uses `returnImmediately: true`. The executor persists the returned
task, then polls `GetTask` until a terminal/interrupted state or a configured
deadline. Idempotent GET failures may be retried within the poll budget. The
client never follows redirects or accepts a task ID different from the expected
one during polling.

Deadline expiry triggers one best-effort `CancelTask`. Cancellation is also an
explicit CLI operator action and records `canceled_by`. Cancel never treats an
already completed task as canceled. An unknown submission cannot be canceled
because no trustworthy remote task ID exists.

## Runtime and routing integration

`AgentProfile.execution_kind` defaults to `local` for backward compatibility.
Without an active deployment, `a2a` profiles are excluded from performance
weighted routing. This prevents registration from granting production traffic.

After benchmark evidence and explicit promotion, an active deployment may name
the exact A2A agent/card identity. `run --allow-remote` loads registered remote
workers; without this opt-in the deployed champion is unavailable and the goal
blocks. The existing local Reviewer still decides PASS/FAIL, and one remote
delegation remains one action under the global `RunBudget`. Network calls are
additionally bounded by the remote policy.

`WorkerBlocked` records a zero-score attempt, marks the task and goal blocked,
and preserves the delegation evidence. It is used for ambiguous submissions,
unsupported interrupted states, and identity drift that cannot be repaired by
an automatic retry.

## Benchmark and promotion integration

`CandidateExecution` and `EvaluationOutcome` gain an optional evidence map.
`A2ABenchmarkRunner` invokes a registered remote executor and records the
delegation ID plus card digest in that evidence. The normal benchmark evaluator
and promotion policy remain unchanged.

Promotion still verifies the `AgentProfile.model_id`; because that ID contains
the card digest, a remote card rotation invalidates the candidate identity.
Remote benchmark execution does not auto-promote and production execution does
not double as an experiment.

## Tracing and audit

Every card inspection, send, poll, and cancel operation produces a redacted A2A
trace span. Span attributes include local delegation ID, agent ID, operation,
task state, byte counts, and poll number, but not URLs containing credentials,
tokens, request content, response content, or private HTTP error bodies.

Delegation transitions are separately queryable through SQLite and CLI. Goal
events link attempts to delegation IDs and active promotion source runs.

## CLI

The CLI adds:

- `agent-society a2a inspect-card URL` for bounded inspection and digest output;
- `agent-society a2a register ...` for immutable operator registration;
- `agent-society a2a agents` for registered trust records;
- `agent-society a2a delegations [ID]` for lifecycle evidence;
- `agent-society a2a cancel ID --by NAME` for explicit cancellation;
- `agent-society run ... --allow-remote` to opt into registered remote workers.

Library users receive `A2AHTTPClient`, `A2ARemoteExecutor`, `A2ARemoteWorker`,
and `A2ABenchmarkRunner` for custom composition.

## Testing strategy

Tests use a real local `ThreadingHTTPServer`, not mocked method calls. They prove:

- exact card digest, interface, skill, protocol, URL, redirect, and auth rules;
- A2A headers and request shapes;
- direct messages, asynchronous tasks, polling, cancellation, and result parsing;
- response, payload, output, poll, and deadline bounds;
- send ambiguity never resends after timeout or process recovery;
- accepted and completed delegation resume behavior;
- input/auth-required blocking and sanitized failures;
- unpromoted remote agents never receive production routing;
- promoted remote execution still passes through local review and budgets;
- benchmark outcomes carry delegation/card evidence;
- SQLite reopen, CLI workflow, package build, and Python 3.10-3.14 CI.

## Non-goals

- Running an A2A server or accepting inbound remote tasks.
- Automatic card trust, trust-on-first-use, crawler discovery, or DNS registry.
- JWS/JCS verification, OAuth acquisition, mTLS provisioning, or credential relay.
- Streaming, Webhooks, push notifications, extensions, or multi-turn input.
- Arbitrary file/media transfer or remote tool exposure.
- Automatic retries of ambiguous Send Message requests.
- Automatic benchmark scoring, promotion, fallback, or online experimentation.
